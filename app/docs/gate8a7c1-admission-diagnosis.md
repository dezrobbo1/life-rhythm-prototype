## Reproduced defect and smallest correction

An isolated real-Chromium probe served the existing app behind a **non-secret, loopback-only synthetic cookie admission layer**. Current source showed “Signed in” but no ordinary content; one request was denied before the downstream handler, whose invocation count was zero. Explicit omit control returned 401 HTML; same-origin control with bearer returned 200 JSON; cookie-only control returned 401. An initial disposable probe installed its middleware after Vite and returned transformed JavaScript with zero counters; it was an invalid harness setup, not evidence, and was corrected before the valid reproduction.

The durable browser regression failed red on the unchanged production client's omit request, then passed after changing only that request to `credentials:'same-origin'` and adding an explanatory comment. This preserves **existing** host-admission cookies rather than extracting, creating or storing real provider credentials. Supabase persistSession:false, token memory lifetime, URL-ingestion prohibition, bearer verification, exact origins, RLS/grants and no-cookie-account-auth remain unchanged. Actual server cookie-only test still returns 401 with zero provider reads. The local admission server's synthetic ready response is a transport fixture, not proof of JWT/provider authorization; genuine server signatures/grants remain covered separately by existing tests.

The cookie mechanism is now a demonstrated code compatibility defect consistent with the hosted symptom, **not a claim that the exact native failure has been proven by unseen request headers**. Native confirmation still needs the new attributable code Preview. No actual cookie value/session/token was read, no parent tab was reset/reloaded and no owner sign-in repetition was requested.
