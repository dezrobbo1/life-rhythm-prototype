# Gate 8A4 — portable canonical profile v1

Base: `697860427cab5008c3c13ef50b4c7201f560932a` (PR #162 merged). This contract describes user-controlled local backup and replace recovery. A Clerk sign-in selects a local namespace; it does not upload the backup or synchronize devices.

## Format and authority

`format: "life-rhythm-portable-profile-backup"`, `formatVersion: 1`, informational `appVersion`, `exportedAt`, and one strict `data` object with every included class. Each class is required; singleton records are nullable. Missing singleton means delete any destination singleton. Future versions, unknown top-level keys and unknown data classes fail. Export and check read only the active namespace. The file belongs to the user; moving it to another browser does not bind it to the former namespace. Existing class-specific check-only artifacts do not acquire restore authority.

The checker rejects input larger than 16 MiB before JSON parsing and caps the aggregate top-level and sidecar collection count at 10,000 before schema traversal. The file picker checks byte length before reading the file. Export fails visibly if its artifact would exceed the same bounds. The checker then validates all rows, duplicate IDs, live rhythm/instance lifecycle relationships, and the static calendar safety boundary before displaying counts. It creates no local data. Import validation uses the adapter's current bounded whole-source BUSY fragment preflight and scheduling's same-window defensive preflight. No calendar provider connection is made. Calendar buffers remain included in the saved source record.

Conflict policy: **replace current local profile**, never merge or choose by timestamp. A non-empty current canonical destination requires typing `REPLACE LOCAL PROFILE`. Preview records a deterministic snapshot of every affected canonical table and scheduler plan row; restore compares the same snapshot inside one write transaction before any mutation. A changed destination must be checked again. Atomic replacement clears affected canonical tables and the derived scheduler plan, then writes the checked backup and, if needed, a minimal repair-pending plan containing only routed rhythm coordinates. A thrown write aborts the whole Dexie transaction. The UI reloads after success to discard pre-restore in-memory state.

Open-ended recurrence safety remains a bounded rolling-horizon guarantee; infinite future occurrences are not enumerated. Restore validates current import horizon under the destination browser's timezone. Legacy or corrupt destination canonical rows are not silently overwritten; repair/export separately first. Live synchronization and cloud backup are outside Gate 8A4.

## Strict v1 snapshots and lifecycle relationships

The v1 checker requires each canonical field in the exporter output to be physically present in the input, recursively, before allowing restore. Persistence defaults and transformations remain useful for legacy rows and normal writes but cannot manufacture missing Settings, nested Life Shape, task/rhythm, preference-day, or calendar-buffer authority during recovery. Genuinely optional fields remain optional; this is not a new database migration.

The Today visibility rule uses the same visible-status helper as lifecycle writes: active, in-progress, paused and Minimum Done are visible, and terminal/not-Today statuses are not. A Pool row marked `today` needs the corresponding visible task by exact ID. Where a Pool/active-task pair exists, its status must agree with the normal transition, including the writer-produced deferred/soft-placed Held cases and the `noLongerNeeded` + skipped special case. Generated rhythm tasks need reciprocal instance identity and the complete status/lifecycle/completion/planning combination produced by normal writers. A routed instance without a linked Today task is invalid; historical unrelated preference and behaviour targets still need not point to live records.

No Task Pool row may share the identity of a generated rhythm Today task, regardless of Pool status. The generated task is an execution projection of the RhythmInstance, not a separate Held intention. A routed live instance bearing `placementId` requires exactly one accepted scheduler placement with that ID and complete matching occurrence identity; exporter refuses unreadable or missing accepted placement data. One shared predicate limits live routing to linked instances in `today`, `inProgress`, or `paused`. Normal closed outcomes preserve historical `activeTaskId` and `placementId` without requiring a live coordinate; the checker rejects an attempt to supply a closed placement as recovery authority. The adjunct contains only selected live accepted placements, never a full scheduler plan. Restore seeds them into a valid private-plan record with pending rhythm repair so `ensureCurrentPrivatePlan` can rebuild and validate the rest under destination inputs. Ordinary scheduler policy may revise a coordinate when canonical constraints have changed; the prior device's full plan is never treated as portable authority.

## Local recovery generation fence

The operational settings sidecar persists the destination's recovery epoch without entering the portable payload. All normal repository read-write transactions share the settings-store lock and compare their captured epoch before the first mutation. Standalone canonical/history/derived-plan writers use the same guarded transaction; Settings Save, Reset, and migration capture before their pre-write settings reads. An old scheduler input snapshot carries the epoch through its settings rows and cannot commit a pre-restore plan after replacement. Recovery-epoch conflicts are not automatically retried on the newly restored profile. Ordinary writes leave the epoch unchanged. Missing metadata means zero without a read-time write; malformed metadata rejects writes and restore. Restore snapshots include the sidecar, then atomically clear and replace canonical and derived rows and increment the destination epoch. A failed restore does not increment it. This fence addresses only recovery replacement, not general Gate 8A5 edit conflict resolution.

Rendered canonical views must carry the generation that preceded their reads into later actions. The bounded audited paths are Today lifecycle/correction; Held lifecycle/correction; Setup Save/Reset; Manual Plan Add/Remove/Undo; Calendar import/remove/buffers; Library rhythm configure/state/Add to Today; explicit preference create/edit/remove/clear; duration-control save/reset; and Reset's saved Today extra-task and destructive behaviour-history delete actions. Behaviour-history deletion retains its own rendered generation while confirmation is typed; a stale rejection clears the confirmation and requires a deliberate new one after refreshing the generation. Read-only behaviour export remains independent. A restore during a source read causes at most one fresh read. Older request results cannot replace newer data and generation. Stale writes abort before mutation, show feedback and refresh the relevant view; old intent is never automatically replayed. Commands that do not derive their target from previously rendered canonical state continue to capture at write start. This local view provenance is not a new global synchronization service.
