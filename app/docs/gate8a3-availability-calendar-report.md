## Verified baseline and implementation

Setup previously rebuilt work hours without `days`, reverting nonstandard weekdays to the schema's Monday–Friday default, and rebuilt fixed commitments from its notes field, discarding hidden timed records. `App.handleSaveSettings` and reset did not mark accepted private plans for repair. Existing profile schemas and seven assignments existed, but ordinary Setup did not expose review/activation. Without a usable envelope the scheduler used explicit `openCapacity`. Plan held one static `.ics` source, whose repository rejected recurring files; imported calendar commitments had zero before/after space. There is no provider OAuth, token backend or live-provider contract.

Setup now offers two same-date usable-day envelopes, seven workday choices, core work hours and their use, four separately entered work travel/transition values, and explicit confirmation on Save. Workday/non-workday IDs and assignment count remain stable. Migration does not activate availability; unchecked/unset boundaries yield no derived candidates. The work period is unavailable, reserved for explicitly classified work intentions/rhythms, or open to otherwise eligible tasks as chosen. Stored `askFirst` remains conservatively unavailable for automatic placement; its explicit decision interaction is deferred. The four work-bound values are **not** inferred from old `commuteMinutes` or `transitionBufferMinutes`; those global fields and meal/wake/sleep anchors remain context. Explicit protected blocks and hard commitments override candidate windows, even if open-capacity blocks overlap. The minimum surviving candidate fragment remains **15 minutes**. Candidate windows are possibilities, not guaranteed capacity. Without activated valid usable day, explicit `openCapacity` remains the compatibility path. Blank calendar time never independently becomes capacity.

Setup preserves timed fixed commitments (IDs, weekdays, intervals, travel, buffers) when editing its separate notes field or another setting; legacy workdays round-trip. Scheduling-relevant settings use a canonical fingerprint and write both settings records and a durable pending repair marker in one Dexie transaction. Cosmetic theme/Start Boost edits do not mark repair. Reset also marks repair when inputs change. A pending repair hides accepted automatic placements; Plan retries the repair. A corrupt derived scheduler plan does not block correction of valid canonical settings. The calendar mutation coordinator retains atomic import/replace/remove repair attention and adds the same transaction boundary for before/after spacing.

## Calendar build-versus-buy and bounded source

We chose pinned `ical.js@2.2.1` (MPL-2.0, browser ESM, bundled TypeScript declarations, maintained recurrence/exception implementation) over writing an RFC 5545 iterator. The adapter validates the particular busy recurrence grammar it relies on and fails closed on unsupported forms. Supported: ordinary nonrecurring VEVENT; FREQ=DAILY/WEEKLY/MONTHLY/YEARLY, INTERVAL, COUNT, UNTIL, BYDAY/BYMONTH/BYMONTHDAY where interpreted by the library; RDATE; EXDATE; single RECURRENCE-ID moved/modified/cancelled exceptions; DATE all-day events; UTC, floating time (explicit warning), and IANA TZID timed events including Sydney DST. BYSECOND/BYMINUTE/BYHOUR/BYWEEKNO/BYYEARDAY/BYSETPOS, unsupported recurrence RANGE, unknown timezone, missing recurring UID/master, malformed or excessive rules fail closed at import and read rather than silently dropping busy future events. Custom TZID not resolvable via the browser's IANA database is rejected even if a VTIMEZONE body is present; source normalization for such exports is a later extension. Expansion returns only occurrences overlapping the requested bounded read horizon, with an upper scan guard. Identity is UID plus original recurrence local identity; override and cancellation keep the logical slot and never duplicate the original. All-day dates remain source-local dates. The source file remains a **static local snapshot**; replace/re-import after calendar changes. No external write occurs.

One version-1 calendar source remains readable without rewriting it and has zero before/after minutes. New imports and spacing edits write version 2 while preserving source content and original imported timestamp on spacing edits; replacement preserves authored spacing. Calendar event location does not infer travel. Source controls appear in Setup and Plan through the same canonical import/remove/write path. A live Google/Microsoft/Apple provider is deferred until Gate 8A4 can define secure credentials and durable data: a local-only browser with no token backend cannot safely promise a managed live connection. The adapter remains provider-neutral.

Settings backup **v3** carries reviewed work-bound context and all existing profile/assignment authority; v1 and v2 backups remain checkable. Restore is still unavailable. Calendar source content stays outside settings backup. Database version remains v6; no destructive migration, reinterpretation of historical commute values, or remote sync is introduced.
