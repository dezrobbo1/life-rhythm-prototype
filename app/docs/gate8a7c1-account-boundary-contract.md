## Selected engineering direction

Propose **existing Clerk identity + a dedicated managed Supabase Postgres project + a small same-origin Vercel Node API within `/app`**. Retain React/Vite and Dexie. Clerk remains the sole login authority; do not add Supabase signup, password login or a second account population. No evidence justifies migrating identity providers.

Supabase provides a supported native Clerk third-party integration and row isolation with Clerk's text subject. Use that integration, not the deprecated shared-secret JWT template. Vercel supplies a small HTTP boundary on the existing app host. This avoids a new always-running application service, custom credential exchange or frontend rewrite. It supports C2 transactions and a later C3 revision boundary while keeping the existing local domain model. Railway/custom servers and a new auth provider add unnecessary operating surfaces for this slice. Engineering selection is proposed here; project/region/plan authorization is not implied.

The app browser calls only the same-origin API. The API verifies the Clerk session, forwards that caller's bearer token with a Supabase publishable key to the Data API, and never substitutes a privileged database/service-role token. RLS still applies if a user calls the provider directly: the API's origin check is not the database authorization boundary. C1 grants only the documented metadata reads; no personal-data table, generic SQL proxy or client mutation permission is exposed. C2 must enforce its transactional validation/revision rules at the database interface too, since an API-only check is bypassable.

## Identity, access and session semantics

1. Accept only `Authorization: Bearer` Clerk **session tokens**, not machine/API/OAuth tokens or user IDs in request headers/body/query. Obtain a fresh token through the current Clerk session API; keep it in memory, never profiles/exports/logs. Cookie-only requests do not authorize this API.
2. Verify signature/algorithm, configured issuer, expiry/not-before, required subject/session ID and exact authorized party with the official backend SDK. Configure a fixed issuer and exact origin allowlist per environment; do not derive trust from a request Host header. Check audience only against an explicitly configured issued audience; do not invent one absent from the current issuer. Reject missing/foreign authorized parties in the application wrapper even if a library treats them as optional. Unknown signing keys/network verification failures deny access; a trusted unexpired cached key may follow the documented SDK path.
3. Derive account identity as `(verified issuer, verified Clerk subject)`; subject is text, not a Supabase Auth UUID. Never authorize from an email, organization selection, hashed database name or user-editable token metadata. Ignore no extra owner field: reject it with 400 so an attempted account override is observable in tests.
4. Require an active, operator-managed `trial_access` row for that identity. C1 exposes no enrollment/admin write endpoint. A valid second Clerk account still needs invitation/access and can never read another account. Disablement is checked on each database read, including direct Data API requests. Missing access is 403 and reveals no account data.
5. For GET, browsers may omit Origin: accept only an approved Origin when supplied; otherwise require `Sec-Fetch-Site: same-origin` and a request URL matching the configured origin. Deny cross-site/foreign origins and requests missing both signals. Future mutation endpoints must require the approved Origin. Do not enable wildcard CORS. Local fixtures use a declared localhost origin. This is additional request protection, not a claim that Origin is an authentication credential.
6. Responses use `Cache-Control: private, no-store`; no CDN/shared cache or request-global user client. Allocate the bearer-bound provider client per request. Sanitize failures and operational logs to request ID, error category, timing and build/version; no token, account email, profile body, task/calendar text or raw provider errors.
7. A locally verified JWT is not instantaneous session-revocation evidence. Record the configured short session-token lifetime and SDK key-rotation behavior in implementation evidence; database access disablement provides an independent denial fence. Sign-out prevents future app requests; copied tokens may remain usable until expiry unless access is disabled. Do not claim immediate universal revocation or refresh-token handling in C1. A requirement for stronger revocation needs an explicit design disposition, not an improvised privileged bypass.

## C1 metadata schema and API

C1 migration defines only `trial_access` and `account_heads`. Both have indexed composite primary key `(issuer text, subject text)`; heads reference access. Access holds `enabled boolean`; heads hold `protocol_version`, `canonical_schema_version`, `revision bigint >= 0`, `generation uuid` and `updated_at timestamptz`. Each head is one account, no content payload. The canonical/schema number is separate from Dexie database version 6 and portable format v1. Initial supported protocol/schema are exactly 1.

Enable and force RLS on both tables. Explicitly revoke default/anonymous/public writes and function execution; grant authenticated SELECT only for these metadata tables. An access row is selectable only for its own verified issuer/subject. A head is selectable only for that same identity **and** an active access row. Check claims with `auth.jwt()` issuer/subject, not `auth.uid()`. Pin the accepted Clerk issuer in provider integration and policies. No security-definer bypass or RLS-bypassing runtime key. Explicit grants and RLS are separate controls and must both be tested. A migration/fixture operator is privileged separately from runtime; credentials are never committed or used by an app request.

`GET /api/account/boundary` takes only required `protocolVersion=1` and `schemaVersion=1`, with optional paired `expectedRevision` and `expectedGeneration`. Reject unknown/repeated parameters, owner/account fields, malformed decimal revisions, missing pairs, unsafe lengths and bodies. Bound query/header parsing. No POST/PUT/PATCH/DELETE capability is enabled by C1 (405).

| Result | Contract |
| --- | --- |
| 200 | Verified active account; return protocol/schema, build ID and `head: null` (no enrollment yet) or `{revision, generation}` from its own compatible head. Do not manufacture a profile or write during GET. Local work remains explicitly device-only at C1. |
| 400 | Invalid request shape/owner override/unsupported syntax; no database mutation. |
| 401 | Missing, expired, forged, wrong-issuer/type/authorized-party session; no database read. |
| 403 | Origin/access denial; no profile or other-account metadata disclosed. |
| 409 | Expected revision/generation differs, or a supplied expectation has no head. Return only the authenticated account's current compatible head; preserve caller work. No repair/overwrite/retry as a new write. |
| 426 | Client protocol/schema differs, or stored head is incompatible. Stable upgrade-required category; do not reinterpret unknown state or manufacture an empty profile. |
| 503 | Missing/wrong backend configuration, provider failure, unreadable/invalid head or unverified boundary. No local-mode fallback or success/durability claim. |

Represent bigint revisions as canonical unsigned decimal strings in JSON/TypeScript (within PostgreSQL bigint range); compare without lossy JavaScript number coercion. Generations are opaque server-issued UUIDs. A successful C1 read does not advance either value. Actual creation, compare-and-swap increment, operation-ID deduplication and reset advancement belong to C2/C3 transactions. C1 provides a pure typed expected-head guard; validation alone is not concurrency protection for a later write. A stale check followed by an unconditional write is prohibited.

## Safe data flow and truthful surface

C1: Clerk receives existing authentication interactions. The browser sends a session token plus version/head expectations to the Vercel API; the API and Supabase receive identity/access metadata only. No task title, settings, behavior history, calendar snapshot or legacy profile leaves the device. Mount ordinary local app content only after a healthy authorized boundary, with clear device-only status; boundary success must not render “synced.” On sign-out or session change, clear boundary response state/abort its requests; never show account A's metadata to B. The full queued/in-flight data-switch protocol remains C3.

C2/C3 target: preview inventory/destination and safe copy → explicit local-profile consent → validated typed account transaction with expected revision/generation and operation ID → durable server acknowledgment → account-bound local replica status. New empty account enrollment must explain future storage before first personal write. C2 defines enrollment/migration acknowledgment; C3 owns durable offline outbox and explicit conflict preservation. Never auto-upload an existing signed-in or legacy profile merely because the user signed in. Same account clean-client hydration follows enrollment; no ad hoc cross-account merge. Retain no unrelated browser profile content remotely.

Provider processing is concrete: Clerk handles identity; Vercel handles authenticated API traffic (later canonical payloads transiently); dedicated Supabase stores later acknowledged personal state and its configured backups. TLS and project at-rest/backups policy must be documented; this is provider-managed protection, not end-to-end encryption. Keep content out of logs/analytics/AI. Before C2 personal data, document region, backup/retention/deletion and privileged operator access honestly; “no admin browsing feature” does not mean provider/operators lack privileged capability. Calendar OAuth/refresh credentials later live server-side outside canonical state/export. No secrets or bearer tokens in VITE variables, bundles, profiles, backups, prompts or evidence.
